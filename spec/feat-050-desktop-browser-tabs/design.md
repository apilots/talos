# Desktop managed browser tabs

## Problem and scope
The bundled Desktop browser currently owns a separate BaseWindow. Agent input preparation brings pages to the foreground, while the right workspace displays unrelated iframe previews. This change embeds managed website WebContentsViews in the product window and separates execution targets from presentation and keyboard focus. It supersedes the independent-window presentation in feat-047 section 4.1.

No new browser engine, automation protocol, media stream, profile store, or dependency family is introduced. Electron moves from 41 to the patched 42 series (minimum 42.9.2, selected 42.11.18). Upstream [#52844](https://github.com/electron/electron/pull/52844) / [42 backport](https://releases.electronjs.org/pr/52865) fixes hidden WebContentsView compositor initialization; retaining 41 would require a local rendering workaround and cannot satisfy this background contract. Docker/noVNC and explicitly connected Chrome retain their existing presentation and authorization.

## Ownership and reuse
- WebsiteAccount continues to own website views, persistent per-account session partitions, CDP senders, downloads and cleanup. It no longer owns a BaseWindow or a separate trusted browser toolbar.
- DesktopBrowserHost retains authorized app-server execution, target selection, cancellation, generation and input fencing. Its existing account owners also serve a narrow local presentation bridge.
- Electron main owns native view attachment, visibility and clamped geometry. The product uses Electron BaseWindow with an explicit trusted product WebContentsView and website views as siblings. BrowserWindow.contentView is an overlay container above its implicit renderer and cannot establish this ordering. The product window factory owns resizing, unload/close cleanup and the trusted renderer inventory used for IPC/events; browser targets stay in their existing account owner. Only the registered product window main frame may access presentation IPC. Website views have no preload or Node access, and remain the only managed automation targets. Website views ignore product menu accelerators only while dispatching synthetic Agent keys; native human editing shortcuts remain available when that dispatch settles, including its failure path. Native JavaScript dialogs are disabled (confirm/prompt are not automatically approved), and website requests to resize/move the product window are rejected.
- The existing Desktop preload and SDK DesktopRendererBridge expose typed local presentation requests and state events. This is not a public server capability and accepts no arbitrary CDP, JavaScript, profiles, files or endpoints.
- RightWorkspace and its existing ephemeral Store own one browser descriptor per native website ID. Host state is reconciled into this store; no parallel persisted tab registry is created. Existing iframe previews on Web remain separate.

## Identity and lifecycle
Binding resolves the actor through the existing authenticated user/current call, never from a renderer-supplied user ID. Binding is scoped to the registered product renderer and an opaque presentation session token. Actor changes, renderer destruction/navigation and host reset withdraw presentation; stale tokens cannot navigate, close or present newer views. State is sent only to the bound renderer for that actor. Cookie/storage partitions retain their existing stable hashed account names and survive target disposal.

New website targets are added as background workspace tabs without selecting them or opening a closed drawer. An explicit Open browser or user-created tab selects its tab and opens the right workspace. Neither path activates the native product window. Closing a native browser tab destroys its target; switching tabs or collapsing the workspace only hides the view. Account/logout/reset cleanup retains the original input-release and target-disposal boundary. Renderer presentation withdrawal does not implicitly cancel a running Turn.

## Focus and background execution
Managed tab focus from model tools selects only the operation target; it never focuses a WebContents or changes the selected workspace tab. Managed creation and navigation disable navigation focus. Agent input uses the existing target-scoped CDP channel and focus emulation without Page.bringToFront. Connected Chrome keeps its existing behavior.

Managed website views disable Electron background throttling and keep a positive last viewport while hidden. Input preparation and post-click completion must not require foreground requestAnimationFrame callbacks. Managed screenshots use Electron capturePage with stayHidden and stayAwake options; connected Chrome retains its existing CDP capture. No hidden BrowserWindow, global input injection, screenshot stream or forced activation is used as a fallback. Real Electron acceptance must exercise detached/hidden and minimized states; an implementation that only passes mock tests is insufficient.

## Presentation
The right Tab strip is the only tab strip for managed pages. A compact toolbar provides address, back/forward and refresh controls using existing shared controls and localization. Main process consumes the shared typed request from the registered product renderer. Existing account methods own target lookup and URL validation; session tokens fence stale requests. Native geometry must be finite and is clamped to product content bounds. Presentation adds no second shape parser, numeric target-ID convention, URL-length cap or fixed maximum screen coordinate. While the product window is not minimized, background tabs remain attached below the opaque trusted product renderer using Electron View sibling ordering. This keeps their compositor and hit-test surfaces live for target-scoped automation while the product renderer covers their pixels and receives native user input. Native setVisible(false) suspends those surfaces and is unsuitable for executing background pages. On macOS, minimizing the product detaches the existing website views from its native hierarchy so macOS does not suspend their compositor; restoring reattaches the same views and the latest requested presentation. On macOS, targets created while minimized remain detached; Linux retains attached background views because detaching removes their input/compositor surface. This changes native attachment only, preserving the targets, viewport, account partitions and login state. Closing an account or replacing/closing its native window removes its minimize/restore listeners. Only the selected website view is ordered above the product renderer within its clamped viewport. DOM hidden/inert does not govern native views; renderer layout observation explicitly synchronizes visibility. Other modal dialogs and overlays must obscure the native view, and responsive drawer changes must not cause passive focus restoration. Browser control settings and pause/resume remain reachable through existing Computer content.

## Validation contract
1. Deterministic host tests cover account/session isolation, stale binding rejection, popup-to-tab behavior, target close/reset/cancel, download preservation and absence of managed OS focus requests.
2. Store/renderer tests cover background tab arrival without focus or drawer changes; explicit reveal; native close; scope reset; geometry/visibility withdrawal and overlay handling. Existing layout focus regressions remain passing.
3. Real Electron acceptance uses a controlled local website and owned temporary profile. It exercises navigation, fill, click, key, scroll, screenshot and popup with the workspace hidden, another owned window focused, and the product minimized; checks window inventory/focus, profile persistence, isolation and target teardown.
4. Existing hosted Desktop browser/resource/MCP scenarios retain this coverage. Existing connected Chrome acceptance remains meaningful and uses an owned temporary profile only.
5. Run scoped SDK/Web/Desktop quality and repository checks; actual results and limitations are recorded only in ignored output/.
