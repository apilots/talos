# MCP 服务管理与可靠性设计

**状态**：草案，代码实施尚未开始
**创建日期**：2026-08-06
**更新日期**：2026-09-07

本轮只修订中文方案与计划，不修改代码、依赖、锁文件或生成产物。[互操作设计](interoperability.md)负责协议、导入和鉴权契约；[根目录实施计划](../../IMPLEMENTATION_PLAN.md)负责阶段、成功标准、测试和状态。

## 目标与范围

本期交付三个结果：

1. 用户在现有设置页面添加 stdio 或 Streamable HTTP MCP，保存为 Plugin manifest，并可启用、禁用、替换和卸载。
2. 单个 MCP 启动慢、挂起、崩溃或协议失败时，Talos 和其他健康 MCP 仍能正常工作，界面能显示真实状态。
3. 升级到已核实的 `rmcp 3.2.0`，适配 MCP `2026-07-28`，完成常见本地命令、HTTP Token/API Key 和本地 OAuth 接入。

本期面向单实例的本地、Desktop 和本地 Web。`mode: cloud` 目前只是部署模式配置，Cloud 多用户、租户、用户凭据隔离、按用户拆分连接和工具目录、托管 OAuth 回调均留到下个版本。本地连接 Notion、GitHub 等第三方托管 MCP 属于本期，与 Talos Cloud 无关。

不新增 `mcp.yaml`。手动 MCP 复用托管安装目录中的 `talos-mcp.json`；现有静态配置保持原有来源，不复制成第二份可写定义。第三方无需制作 Talos 专用插件包。

## 收敛原则与取舍

| 原方案中的设计 | 本次决定 | 理由 |
| --- | --- | --- |
| 启动器 trait、多执行器与 sidecar 扩展点 | 删除预建框架，只保留本地进程管理职责 | 当前只有一个真实执行方式；stdio 已经是子进程 |
| 多客户端配置方言、批量预览、批量事务结果 | 缩为一次添加一个服务，支持表单及常见 JSON 片段 | 解决复制配置即可接入，不建设通用配置转换系统 |
| 通用凭据中心与独立凭据 CRUD API | 缩为服务设置中的只写凭据，以及必要的 OAuth 操作 | 当前调用方只有 MCP 服务管理 |
| manifest 中统一可调启动、操作、收尾策略 | 暂缓新增配置对象和界面 | 先复用现有期限并补齐缺失期限，不制造配置面 |
| 全新环境允许列表、强制分类迁移全部旧 manifest | 移出本期 | 复用现有环境过滤；新凭据安全接入不应依赖全仓配置迁移 |
| 强制服务名称改为小写 | 删除 | 沿用现有名称规则，避免无必要的不兼容 |
| 启动时预取全部资源和模板 | 删除 | 资源通过已有接口按需获取，不应决定工具是否就绪 |
| 新交互输入系统、Prompts、Sampling、MCP Apps、任务扩展 | 后置，不宣告支持 | 升级规范不等于实现全部可选能力 |
| 后台启动、代次校验、目录原子更新、进程树清理 | 保留 | 分别解决主流程阻塞、旧任务回写、目录不一致和子进程残留 |
| HTTP 鉴权与本地 OAuth | 保留 | 是主流远程 MCP 的实际接入要求 |

本期也修正现有 MCP 模块中直接阻碍这些目标的设计。不会为了统一命名、目录或配置形状重构全部插件、工具或错误系统。

## 当前代码事实与具体改动点

代码核对日期：2026-09-07。下表描述现状和待实施改动，不代表代码已经修复。

| 现有位置 | 当前问题 | 最小改动 |
| --- | --- | --- |
| `talos-rs/crates/action/mcp/src/lib.rs` | `refresh()` 串行连接并替换、关闭全部服务 | 原运行时按定义差异协调，有界后台启动，只处理新增、变更和删除 |
| 同上 | 服务表读锁跨网络等待；失败只保留消息 | 捕获服务句柄后释放锁；内部保留强类型错误，对外投影 `ApiError` |
| 同上 | stderr 未持续读取，缺少完整进程树清理 | 复用 SDK 进程能力，补齐排空、退出观察和有界清理 |
| 同上 | 启动期间预取资源；列表忽略后续页；部分操作无期限 | 就绪只依赖必要协议流程与工具发现；资源按需分页，操作均有期限 |
| 同上 | HTTP 构造忽略 headers，协议版本固定 | 使用新版 SDK 协商与传输构造，真实应用 headers 和鉴权 |
| `talos-rs/crates/action/tools/src/mcp/mod.rs` | `McpConnectionManager` 永久缓存快照和工具定义 | 保留工具适配职责，删除永久副本；连接事实归运行时，工具投影归注册表 |
| 同上及 `handlers/mcp.rs` | 资源接口忽略 cursor；丢弃结构化结果；图片退化成 JSON/base64 | 转发有界分页，保留结构化结果，复用已有强类型内容与产物链路 |
| 同上 | 全部 MCP 工具默认只读、非破坏性、可并行；有占位死代码 | 使用现有保守权限规则，annotations 仅作提示；删除占位与被替代路径 |
| `talos-rs/crates/action/tools/src/registry.rs` | 只有注册，缺少 MCP 投影替换 | 原子替换 MCP 命名空间，保持内置和动态工具职责 |
| `talos-rs/crates/app/talos-base/src/lib.rs` | 空目录时不创建运行时，启动等待全部连接，静态 HTTP 鉴权转换缺失 | 启用 MCP 时始终创建运行时；应用组装统一定义并发布；补齐鉴权转换 |
| Plugin 安装器、manifest 扫描及 `PluginManagerService` | 没有手动安装目标，修改不协调运行时，一个坏 manifest 可阻断全部发现 | 扩展原安装目标、复用校验与事务；修改后协调；按安装隔离发现错误 |
| `SettingsMcpServersSection`、`McpServerForm` 及共享 SDK | 保存尚不可用，只有安装状态 | 接通现有表单及 JSON 输入，展示运行和鉴权状态，复用错误展示器 |

只按这些真实职责拆分过大的 MCP 文件，例如连接生命周期、本地进程处理和协议结果转换；不预建空模块、通用 factory 或新 manager。`McpConnectionManager` 可以收缩为工具适配器，是否改名由实际调用面决定，不将全仓改名作为交付条件。

序列化或协议转换中的 `unwrap_or`、`.ok()` 等静默丢失行为，在本次触达的结果链路内改为有来源的显式失败；不扩展成全仓错误重构。

## 职责与核心对象

| 边界 | 唯一职责 | 禁止承担的职责 |
| --- | --- | --- |
| Plugin 生命周期 | 定义、安装状态、启用、替换、卸载及持久化事务 | 持有进程、SDK 客户端或 OAuth 会话 |
| 现有应用/Service 组装层 | 合并静态与插件定义、校验冲突、解析服务凭据、触发协调 | 实现 MCP 协议或另建管理体系 |
| `TalosMcpRuntime` | 当前连接、运行状态、工具发现、本地进程、调用和资源访问 | Plugin 安装和 UI 展示 |
| 现有 MCP 工具适配模块 | 将协议结果和工具定义接入现有工具系统 | 再缓存一套永久连接状态或管理进程 |
| `ToolRegistry` | 当前模型可见的工具定义和处理器 | 连接、重连、关闭 |
| 设置页面和 SDK | 输入及真实状态展示 | 直接改文件、推测连接状态、重做后端校验 |

继续复用 `McpServerDefinition`、传输定义、运行时描述符和快照。输入格式只在入口适配，SDK 类型保持在 `talos-mcp` 内。不要为 UI、手动安装和市场来源分别复制同一套 MCP 对象。

运行时以现有来源身份区分静态配置键和 Plugin 安装 ID；服务名称仍用于工具命名空间，实例内必须唯一。仅在内部需要时以强类型身份表达这一边界，不引入用户字段或新的身份注册表。变更检测优先比较规范化后的强类型定义，复用已有摘要；不新增哈希框架。

配置、来源、安装方式、鉴权与运行状态分开表达，但分开建模不等于每种状态都需要独立服务或存储。

## 手动 MCP 管理

### 安装与更新

扩展现有 `PluginInstallTarget`，增加携带 `McpServerDefinition` 的 `ManualMcpServer` 目标。继续使用现有 `PluginInstallRequest`、`PluginInstallResponse` 及插件列表、读取、启用、禁用、卸载接口。

安装器生成 `PluginKind::McpServer`、`PluginInstallSource::Manual` 的托管安装，在现有目录保存 `talos-mcp.json`，复用市场 MCP 的 manifest 读取路径。定义持久化与安装状态写入复用已有锁、临时文件、原子替换和恢复机制。

服务名称沿用现有校验器，包括现有允许的大小写，不静默改名。安装路径由安装器从已校验身份派生并检查不越过安装根目录，不能直接拼接未经校验的输入。手动输入的非空 `cwd` 必须为绝对路径；市场 manifest 的相对路径继续按安装目录解析。

同名手动安装遵循既有 Reject/Replace 语义。修改传输定义走已有替换安装流程，不新建一套更新协议；前端应提供重新提交替换的可达路径。市场安装继续遵循原有更新方式。

现有 Service 层在提交前检查候选定义是否与静态配置或其他安装冲突。Plugin 管理器不反向读取应用配置。安装成功表示定义已经保存，不保证依赖已安装或连接已就绪。

### 发现与故障隔离

已安装 manifest 按安装逐项解析。一个损坏安装产生结构化插件警告并排除该项，不能阻断其他安装。优先复用已有发现结果和 `PluginWarning`；只有现有返回类型无法承载部分成功时才增加内部结果对象，不公开新的发现 API。

静态配置仍在配置提交前整体验证。非法修改不替换当前生效定义，也不触发协调。两者不能通过吞错或伪造运行时快照实现。

### 凭据与启动环境

凭据规则见[互操作设计](interoperability.md)。新 Token/API Key 输入只写，manifest 保存引用；敏感数据不进入快照、日志、导出或模型上下文。

stdio 保留 command、参数数组、env 和 cwd。复用 `env_clear()`、现有 `filter_inherited_tool_environment()` 及显式变量注入；本期不新增通用 `inherit_env` 配置和整机环境策略。新增秘密引用必须显式解析并只注入对应服务，引用缺失明确失败。命令不通过 shell 字符串拼接，记录执行主机及启动配置来源。

`npx`、`uvx`、Docker 和直接可执行文件都按 command/args 启动，不新增包管理器适配器或自动安装服务。现有环境过滤不等于资源沙箱，系统环境中仍可能存在无法通过名称识别的敏感值。

## 运行时行为

### 后台启动与状态

启用 MCP 功能时，即使初始服务目录为空也创建运行时。应用发布期望服务目录后即可对外可用；最多同时启动四个连接，其余任务可在创建进程前取消。并发限制放在现有运行时内，不新增调度器。

需要授权但没有可用凭据的服务保持 `NotStarted`。其余服务进入 `Starting`，在总启动期限内完成 SDK 协商/发现，并在服务声明工具能力时完成必要的工具列表读取后进入 `Ready`，失败则进入 `Failed`。未声明工具能力的服务可以带空工具目录就绪，不能因此拒绝仅提供资源的 MCP。资源、模板不在启动路径上预取，不作为工具就绪条件。

运行状态最小扩展为 `NotStarted`、`Starting`、`Ready`、携带安全错误的 `Failed` 和 `Exited`。内部失败保存 `TalosError` 与强类型来源，对外快照仅投影 `ApiError`，遵循[统一错误模型](../../docs/architecture/ERROR_MODEL.md)。

`Exited` 仅表示就绪后本地进程非主动关闭的退出；启动期间退出属于 `Failed`。HTTP 无本地进程，不产生 `Exited`。主动清理不覆盖原始失败状态。已禁用安装通过 Plugin 状态展示，不另外维护一套运行时禁用状态机；已有公开 `Disabled` 值是否移除按兼容审查处理，不为本期强行删字段。

### 增量协调与目录一致性

现有应用/Service 组装层在安装、替换、启用、禁用、卸载、有效配置重载及鉴权变化后，统一构造期望服务目录并调用原运行时协调入口。

| 差异 | 行为 |
| --- | --- |
| 未变化 | 复用现有连接和工具目录，不重连 |
| 新增 | 按鉴权状态发布 `Starting` 或 `NotStarted`，后台启动 |
| 变更 | 立即撤下旧工具，按新定义启动；只处理该服务 |
| 删除 | 拒绝新调用并撤下工具，后台清理旧连接 |

所有会改变期望目录的修改经现有 Service 层同一个临界区完成校验、准备、持久化提交和内存发布；不在其中等待外部 MCP。提交前完成可失败的定义校验。提交后协议启动失败只改变运行状态，不能把已经成功的安装伪装成失败或回滚安装。

运行时状态与 MCP 工具投影按同一代次协调发布。注册表先构造完整下一版 MCP 投影，再原子替换；发现只能看到完整旧版或新版，内置和动态工具不受影响。发布中的旧处理器也必须通过运行时校验服务身份与代次，不能误调用变更后的同名工具。

每个后台启动、调用、退出或清理任务只能影响捕获的服务代次，旧任务不能回写新状态。服务表锁只用于捕获句柄和代次，网络等待在锁外执行。注册表拥有当前工具投影，适配器不再保存永久快照。

变更或删除时，已捕获旧句柄的普通在途调用允许在有界期限内结束，新调用立即拒绝。鉴权断开需阻止新请求并取消关联在途请求，不能继续使用已移除凭据；其他服务不受影响。SDK 成功刷新 token 不改变工具身份，也不无故重置连接。

工具目录变化使用协商后的 SDK 通知/订阅，只刷新关联服务。沿用现有工具可用性检查和增量上下文链路，不重写模型历史，不新建事件总线或缓存框架。

### 本地进程与关闭

stdio 已经运行在独立子进程中。先核对升级后 SDK 的子进程句柄、退出通知和清理能力，能满足目标就直接复用。只对 SDK 缺少的进程树控制补充私有本地实现；不要求强行把子进程所有权从 SDK 拆走，不预建 launcher trait、executor factory 或 sidecar。

进程处理必须满足：

- stderr 持续排空，读取缓冲有界；第三方原始文本默认不转发到普通日志、UI 或模型，退出及 I/O 元数据使用结构化错误边界。
- 观察异常退出，区分主动清理与自然退出。
- 启动失败、取消、禁用、卸载和主程序正常关闭均有进程树清理路径；初始化部分失败也不能遗留已启动进程。
- 有明确的关闭期限和平台行为。Unix 进程组、Windows 对应进程树机制分别验证；清理次级失败单独报告。

不承诺隔离 SDK 客户端自身崩溃、CPU/内存耗尽、文件系统或网络权限。完整进程隔离与资源配额需要独立产品需求，本期不预留框架。

### 期限与错误范围

沿用默认启动 30 秒、操作 120 秒，旧连接收尾最多 120 秒。期限集中在现有运行时内部，测试可显式覆盖；本期不新增 manifest 执行策略对象或通用超时调节界面。启动从出队开始计时，覆盖进程创建、协议发现和全部必要工具分页。一次工具目录刷新共享总操作期限；资源单页读取和内容读取分别受操作期限限制。

请求取消的通知发送和本地收尾也必须有界，不能在原请求超时后无限等待取消。禁止自动重试有副作用的工具调用，也不新增自动重连循环。服务失败可通过禁用/启用恢复。

| 结果 | 影响 |
| --- | --- |
| 参数错误、远程拒绝、`is_error`、不支持的可选能力 | 单次操作失败，保留可用连接 |
| 调用取消或超时 | 按 SDK 语义取消，不能仅凭超时认定整台服务失效 |
| 终止性传输失败 | 移除该代次工具，发布 `Failed` 并清理 |
| 本地就绪进程退出 | 发布 `Exited` 并移除该代次工具 |
| 鉴权失效或断开 | 阻止该服务未授权调用，展示鉴权状态 |

`is_error` 属于服务返回的工具结果：保留完整强类型内容、结构化数据与错误标志交给工具适配器，不能降成只有 `ApiError` 的调用失败。错误分类依赖类型与错误码，不匹配远程消息文本，不用空目录或空成功结果掩盖失败。

## API 与前端改动

保留现有设置页面，不新建管理中心。表单与 JSON 输入共用后端安装校验和规范对象；替换、启用、禁用、卸载复用插件 API。字段和不支持的配置必须有明确错误。

新增 API 限于当前真实缺口：手动安装目标、运行时快照查询、服务设置中的只写凭据，以及 OAuth 启动/状态/断开。优先扩展现有服务接口，不新增独立导入预览 API、凭据目录 API、批量操作 API 或重启 API。规范 Request/Response 跨 HTTP、JSON-RPC、SDK 和前端复用。

运行时快照列表遵循现有 cursor/limit 和 data/next_cursor 规则，使用不透明游标与有界页面。Plugin 行按安装 ID 关联快照，静态服务保留配置来源，不伪造安装记录。快照不携带解析后的秘密值。

界面分别展示安装/启用、运行、鉴权状态。加载中、尚需授权、损坏 manifest 和运行失败必须有真实依据；缺失快照不能直接解释为就绪或禁用。后台启动意味着首次 turn 可能只看到已经就绪的服务，界面明确显示启动中。

影响公共对象时由生成命令更新当前主版本 schema、Rust/TS SDK、示例和调用方；不手写生成产物，不给旧协议增加新入口。

## 兼容影响与验收约束

- 保留现有名称大小写规则、静态配置来源、环境过滤默认行为及 Plugin 生命周期，不制造无关迁移。
- 新凭据字段与状态对象变化需要 schema 和调用方同步。旧静态 bearer 配置经显式适配实际生效，不继续忽略；不将旧秘密复制到新 manifest 或公开输出。
- 只针对真实存在的凭据形态设计必要转换，不要求所有旧 env/headers 一律重新分类。新导入的秘密必须安全落盘，旧定义的读取与展示也必须继续脱敏。
- 后台启动及目录即时更新属于行为变化，必须验证早期 turn、在途调用、启用/禁用、错误事件和会话回放。
- 资源列表从旧裸数组改为带游标的强类型页面属于工具输出契约变化，必须同步现有工具说明、调用方和回放测试，不能只修改后端返回值。
- 升级依赖同时更新工作区与锁文件，并检查所有直接使用 `rmcp` 的模块和测试服务。
- 验证复用现有 MCP 测试二进制、工具集成 fixture、前端测试和 `talos-e2e/scenarios/09_app_server/mcp_e2e.sh`。不为新模块布局、静态配置常量或删除的代码写形式测试。
- 主流服务兼容性以[互操作验收矩阵](interoperability.md#验收证据)为准。文档完成、依赖升级、编译成功均不等于实际接入完成。

实施阶段与检查命令只在[根目录 PLAN](../../IMPLEMENTATION_PLAN.md)维护，避免两份执行状态漂移。
