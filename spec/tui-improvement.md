## 1. 现状分析

### 1.1 当前能力评估

| 功能 | 状态 | 备注 |
|------|------|------|
| 流式对话（SSE） | ✅ 完整 | 增量 append，支持停止 |
| 网关模式（Remote） | ✅ 完整 | HTTP + SSE，自动重试 |
| 嵌入模式（Embedded） | ❌ 未接线 | 代码占位符，无实际 Agent 调用 |
| 思考过程显示 | ✅ 完整 | 灰色斜体展示 reasoning_delta |
| 工具事件展示 | ⚠️ 基础 | 仅显示事件名，无输入/输出详情 |
| 工具审批交互 | ❌ 缺失 | approval 流程 TUI 端完全未实现 |
| 消息队列 | ✅ 完整 | 最多 3 条排队，自动重试 |
| 鼠标选择复制 | ✅ 完整 | 拖选自动复制到剪贴板 |
| 会话管理（创建/切换/关闭） | ✅ 基础 | 通过斜杠命令操作 |
| 历史会话浏览 | ❌ 占位符 | UI 框架存在，无实现 |
| 设置面板 | ❌ 占位符 | UI 框架存在，无实现 |
| Markdown 渲染 | ❌ 无 | 纯文本展示 |
| 代码块高亮 | ❌ 无 | 无语法着色 |
| 持久化配置 | ❌ 无 | 每次启动重置 |

### 1.2 架构问题

1. **`lib.rs` 4005 行单文件**：UI 渲染、事件处理、业务逻辑、测试全部混在一起，维护困难
2. **嵌入模式断路**：`ConnectionMode::Embedded` 分支硬编码返回占位符消息，是 MVP 的核心阻塞
3. **工具审批流程缺失**：后端已实现 `POST /v1/sessions/{id}/tool-approvals`，但 TUI 端未接入，导致工具审批功能在 TUI 下完全不可用
4. **右侧面板工具事件只增不减**：工具事件累积展示，无清理策略，长会话后面板会被撑满

### 3.3 工具审批交互

这是当前 TUI 最大的功能缺口。当 Agent 需要执行需审批的工具时，TUI 应暂停输入并展示确认卡片：

**审批等待状态**（渲染在对话区，替换输入框焦点）：

```
  ┌─ 🔧 exec_command ─────────────── ⚠️ 需要确认 ─┐
  │                                               │
  │  即将执行命令：                                │
  │  rm -rf /tmp/old_build                        │
  │                                               │
  │  该操作不可逆，请确认是否继续                  │
  │                                               │
  │  [y / Enter：批准]        [n / Esc：拒绝]     │
  └────────────────────────────────────────────────┘
```

键盘交互规则：
- `y` 或 `Enter`：批准，调用 `POST /v1/sessions/{id}/tool-approvals`（`approved: true`）
- `n` 或 `Esc`：拒绝，调用同接口（`approved: false`）
- 审批期间输入框锁定，不接受其他输入

状态机：
```
对话进行中
  → 收到 MessageToolCallPendingApproval 事件
  → 渲染审批卡片，锁定输入框
  → 用户按 y/n
  → 发送 tool-approvals 请求
  → 解锁输入框，继续等待 AI 响应
```

### 3.4 Markdown 渲染（基础版）

终端无法改变字号，但可以用样式和特殊字符模拟 Markdown 层次感：

| Markdown 元素 | 渲染方式 | ratatui 实现 |
|--------------|---------|-------------|
| `**粗体**` | 粗体文字 | `Style::BOLD` |
| `*斜体*` | 斜体文字 | `Style::ITALIC` |
| `` `行内代码` `` | 深色背景 + 浅色文字 | `bg: Rgb(40,44,52)` |
| `# 标题` | 粗体 + 全大写 + 前缀 `▌ ` | `Style::BOLD` |
| `## 二级标题` | 粗体 + 前缀 `── ` | `Style::BOLD` |
| `- 列表项` | `• ` 前缀 + 缩进 2 列 | 字符替换 |
| `1. 有序列表` | `1. ` 前缀 + 缩进 3 列 | 字符替换 |
| `> 引用` | 左侧 `│ ` + 灰色文字 | `fg: DarkGray` |
| 代码块 | 带语言标签的边框块 | 见下方 |
| `---` 分割线 | `────────────────` | 字符替换 |

**代码块渲染示例**：

```
  ┌─ rust ────────────────────────────────────────┐
  │ use std::collections::HashMap;                │
  │                                               │
  │ fn main() {                                   │
  │     let mut map = HashMap::new();             │
  │     map.insert("key", "value");               │
  │ }                                             │
  └───────────────────────────────────────────────┘
  [y: 复制代码]
```

**代码语法高亮**（有限支持）：
- 关键字（`fn`, `let`, `mut`, `use`, `if`, `match` 等）：`Color::Blue + Bold`
- 字符串字面量：`Color::Green`
- 注释：`Color::DarkGray + Italic`
- 数字字面量：`Color::Cyan`
- 类型名（大写开头）：`Color::Yellow`

实现方案：轻量手写 tokenizer（避免引入 `syntect` 等大依赖），仅支持 Rust / Python / Shell 三种高频语言，其余语言以纯文本展示。

## 5. 代码结构重构建议

当前 `lib.rs` 4005 行是维护的主要障碍。建议按职责拆分：

```
apps/ui-tui/src/
│
├── main.rs                     # 入口：CLI 参数解析 + 初始化（< 130 行）
│
├── app.rs                      # TuiApp 核心状态定义（< 200 行）
│                               # 只保留字段和构造函数
│
├── run.rs                      # 事件循环（on_tick + 渲染调度）
│
├── ui/                         # UI 渲染（只负责"画"，不含业务逻辑）
│   ├── mod.rs
│   ├── layout.rs               # 全局布局计算（左/中/右区域分割）
│   ├── sidebar.rs              # 左侧导航栏（图标列）
│   ├── chat_panel.rs           # 对话区（消息列表 + 工具卡片）
│   ├── tool_card.rs            # 工具调用折叠卡片渲染
│   ├── right_panel.rs          # 右侧状态/工具面板
│   ├── input_box.rs            # 输入框 + 状态栏
│   ├── history_panel.rs        # 历史会话面板
│   ├── model_picker.rs         # 模型切换浮层
│   └── approval_card.rs        # 工具审批确认卡片
│
├── events/                     # 输入事件处理
│   ├── mod.rs
│   ├── keyboard.rs             # 键盘事件 → App 动作
│   └── mouse.rs                # 鼠标事件 → App 动作
│
├── stream/                     # 流式响应处理
│   ├── mod.rs
│   └── handler.rs              # TalosEvent → App 状态更新
│
├── markdown/                   # Markdown → ratatui Line 渲染器
│   ├── mod.rs
│   ├── parser.rs               # 简易 Markdown 解析
│   └── highlighter.rs          # 代码语法高亮（Rust/Python/Shell）
│
├── history.rs                  # 历史会话加载和管理逻辑
│
└── client_integration.rs       # 保持现有（Gateway 客户端调用）
```

**拆分原则**：
- `ui/` 目录下的文件只负责将数据渲染成 ratatui `Widget`，不包含任何业务判断
- 业务逻辑（发送消息、切换模型、审批工具等）保留在 `app.rs` 和各功能模块中
- `events/` 将键盘/鼠标原始事件转换为语义化的 `AppAction` 枚举，与渲染解耦

## 7. 与 Web UI 的关系

TUI 和 Web UI 面向不同使用场景，但共享同一套 Talos Gateway API：

| 能力 | TUI | Web UI | 共用 API |
|------|-----|--------|---------|
| 流式对话 | ✅ | ✅ | `POST /v1/sessions/{id}/messages` |
| 工具审批 | P0 补齐 | ✅ | `POST /v1/sessions/{id}/tool-approvals` |
| 会话历史 | P1 补齐 | ✅ | `GET /v1/sessions` |
| Memory 管理 | — | ✅ | `GET/POST/DELETE /v1/memory`（后端需新增） |
| 文件管理 | — | ✅ | `POST/GET /v1/files`（后端需新增） |
| 设置管理 | 本地配置文件 | Web 界面 | 部分 |
| 模型切换 | `Ctrl+M` 浮层 | 下拉菜单 | `PATCH /v1/sessions/{id}` |

**TUI 核心优势**：
- **零延迟启动**：无需浏览器，终端直接运行
- **SSH 友好**：可在远程服务器上使用
- **开发者原生**：键盘驱动，与代码编辑器工作流无缝衔接
- **低资源消耗**：无 Electron/Chromium 开销

TUI 的优化不应追求与 Web UI 功能等价，而应聚焦于**开发者/命令行用户的高效工作流**。Memory 和 Files 管理这类偏向"浏览/管理"的操作，在 TUI 中做简化版即可，核心是对话和工具执行体验。
