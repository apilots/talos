## 1. 设计背景与目标

### 1.1 产品定位

Talos Web UI 是 Talos AI 智能助理框架的 MVP 对外产品界面。目标用户是有一定技术背景的个人用户，期望一个干净、专注的 AI 工作伙伴，而非功能堆砌的平台产品。

### 1.2 系统架构定位

Talos 采用**服务端常驻模式**，客户端（TUI / Web / Electron Desktop）均为观察与控制窗口，不持有业务逻辑。

```
┌─────────────────────────────────────┐
│         Talos Server（常驻）         │
│  Agent Kernel · Memory · Tools      │
│  HTTP API + SSE Event Stream        │
└──────────┬────────────┬─────────────┘
           │            │
    ┌──────┴───┐  ┌─────┴──────────┐
    │   TUI    │  │  Web / Electron │
    │ 已有客户端│  │   本文档范围    │
    └──────────┘  └────────────────┘
```

**核心含义**：
- Agent 可以在用户不在线时自主运行任务
- 所有客户端状态以 Server 为准，通过 SSE 实时同步
- 工具审批是**阻塞型**操作，Agent 等待用户响应后才继续

### 1.3 设计原则

| 原则 | 说明 |
|------|------|
| **Agent 优先** | 界面服务于"观察和控制 Agent"，而非被动等待用户输入 |
| **权限内联提示** | 工具审批直接在消息流内处理，无权限则就地提示并引导配置 |
| **简洁克制** | 不展示用户不需要的信息；每个页面只有一个主要焦点 |
| **对话优先** | 所有设计服务于"对话"这个核心动作，功能管理退居侧边 |
| **响应及时** | 流式输出、即时反馈，让用户感受到 AI 在实时工作 |
| **信息分层** | 主要内容突出，辅助信息轻描淡写，绝不喧宾夺主 |
| **暗色基调** | 深色主题，长时间使用不疲劳；参考 Linear、Raycast 的审美 |

### 1.4 参考产品分析

| 产品 | 借鉴点 | 避免点 |
|------|--------|--------|
| **ChatGPT** | 对话区宽度控制、消息气泡风格、左侧历史列表分组 | 功能入口过多、左栏视觉重 |
| **Claude.ai** | 侧边栏收缩/展开、文件上传入口克制 | 欢迎页信息过多 |
| **Linear** | 整体暗色风格、字体层次、图标极简 | — |
| **Raycast** | 快捷键驱动、搜索优先、交互响应快 | — |
| **Notion AI** | 内联工具调用展示风格、思考块折叠 | — |

## 2. 信息架构

### 2.1 核心概念：Project 与 ProjectRoot 类型

所有会话（Session）都必须归属于一个 **Project**。Project 是 Talos 工作的根上下文，
详细语义参见 `spec/project-root-workspace-semantics-design.md`。

```
Project
├── root: ProjectRoot  ← 强类型，见下方定义
├── name               展示名（如 talos）
└── Sessions[]
```

**ProjectRoot 三种类型**，前端必须强类型区分，不允许泛用字符串路径：

| 类型 | 语义 | 允许的运行模式 |
|------|------|--------------|
| `managed_workspace` | 由 Server 管理，路径 `~/.talos/workspace/{name}/`，Server 自动创建 | Web + Electron 云端 + Electron 本地 |
| `server_visible_path` | 用户输入的路径，Server 进程可直接访问（例如服务器上的 `/home/xu/project`） | Web + Electron 云端 |
| `desktop_local_path` | 用户本机路径，只有 Electron 本地内嵌模式下的 Server 进程可访问 | **仅 Electron 本地模式** |

**Web 端限制**：只允许创建 `managed_workspace` 和 `server_visible_path` 类型的项目。
`Add new project` 弹窗在 Web 端不展示本机文件选择器，路径栏标注「请输入 Server 可访问的绝对路径」。

**"Add new project" 弹窗按运行模式差异化**：

```
Web / 云端模式:
  项目类型: [● 托管工作区]  [○ 指定服务端路径]
  路径:     ~/.talos/workspace/my-project  (托管时自动填充，不可编辑)
         或  /home/xu/dev/project           (指定路径时手动输入)

Electron 本地模式:
  项目类型: [● 托管工作区]  [○ 指定路径]
  路径:     ~/.talos/workspace/my-project
         或  /Users/xu/dev/project  [📂 浏览]  ← 本地模式才有文件选择器
```

### 2.2 顶层导航（左侧边栏）

侧边栏结构极简，**去掉 ACTIVE / RECENT 时间分组**，以 Project 为维度展示 Threads（会话列表）。

```
┌─────────────────────┐
│  ⬡ Talos            │
│  ● 已连接  12ms     │
├─────────────────────┤
│  Threads    ≡  ✎    │  ← 标题 + 过滤图标 + 新建会话图标
├─────────────────────┤
│  ⌥ talos            │  ← 当前项目的会话列表（扁平，无时间分组）
│  ⌥ 重构模块依赖     │
│  ⌥ bug 排查记录     │
│  ⌥ 编写单元测试     │
│  ⟳ 分析项目架构     │  ← 运行中的会话（蓝色图标）
│  ⏸ 部署前检查       │  ← 等待审批（橙色图标）
│                     │
│  ─────────────────  │
│                     │
│  🗂 Memory          │
│  📁 Files           │
│  ⚙️  Settings       │
├─────────────────────┤
│  👤 账户            │
└─────────────────────┘
```

**设计说明**：
- Threads 列表展示**当前项目**下的所有会话，扁平排列，不分 Today/Yesterday
- 会话图标 `⌥` 为默认态（已完成/空闲），`⟳` 运行中，`⏸` 等待审批，`✗` 出错
- 切换项目时，Threads 列表跟随刷新为该项目的会话
- 当前项目名显示在欢迎页标题中（见 3.1 节），侧边栏不重复展示项目名
- hover 会话条目时右侧出现 `···` 菜单（重命名 / 删除）

**会话状态说明**：
- `⌥` 灰色：已完成 / 空闲
- `⟳` 蓝色转圈：Agent 正在执行任务
- `⏸` 橙色暂停：等待工具审批，Agent 已阻塞
- `✗` 红色叉：执行中发生错误

### 2.3 主要页面

| 页面 | 路由 | 核心功能 | 用户类型 |
|------|------|---------|---------|
| **Chat（新建）** | `/` | 项目选择 + 新建会话欢迎页 | 普通用户 |
| **Chat（会话）** | `/sessions/:id` | 对话界面（含工具审批内联） | 普通用户 |
| **Memory** | `/memory` | 查看/编辑/删除记忆 | 普通用户 |
| **Files** | `/files` | 文件管理与引用 | 普通用户 |
| **Settings** | `/settings` | 服务器连接、模型、权限配置 | 普通用户 |
| **Admin** | `/admin` | 系统管理后台 | 管理员 |

#### Project Bar（顶部项目栏）

对话页面顶部固定一条轻量项目栏，展示当前 project 上下文：

```

│  ⌥ talos  ·  /Users/xu/data/ailabs/talos        New chat  ···       │
└──────────────────────────────────────────────────────────────────────┘
```

- `⌥ talos` 可点击，打开项目切换下拉（同欢迎页项目选择器）

- `···` 展开当前会话操作（重命名、删除、查看项目路径）

**底部工具栏两侧控件**（参考 Claude Code 输入框底栏设计）：

左侧：**运行模式选择器** `☁ 云端 ▾`

```
┌─────────────────┐
│ ✓ ☁ 云端       │  ← 连接远端 Talos Server（默认）
│   □ 本地        │  ← 内嵌模式：在本机启动 Talos Server 进程
└─────────────────┘
```

| 模式 | 说明 |
|------|------|
| **云端**（默认） | 连接 Settings 中配置的远端 Talos Server，适合服务器常驻场景 |
| **本地** | 前端内嵌启动一个本地 Talos Server 进程（类似 TUI 模式），无需独立部署，适合 Electron 单机使用 |

切换到本地模式时，侧边栏连接状态更新为 `● 本地  进程中`；切换到云端时恢复 Server 地址连接。

右侧：**审批策略选择器**（server-evaluated）

前端**不自行定义权限语义**，选项由服务端 `GET /v1/sessions/{id}/effective-policy` 返回，
对齐后端 `ToolApprovalRequirement`（见 `spec/governance-protocol-collaboration.md`）。

```
┌──────────────────────────────────────────┐
│ ✓ 按需审批（needs_approval）              │  ← 默认，敏感工具逐次确认
│   跳过审批（skip）                        │  ← 所有工具自动允许（需服务端授权）
│   ─────────────────────────────────────  │
│   ⓘ exec_command 始终需要审批（系统锁定） │  ← 服务端 locked 工具不受此切换影响
└──────────────────────────────────────────┘
```

**接口契约**：

```typescript
// 获取当前会话可用的审批策略（服务端按用户权限决定）
GET /v1/sessions/{id}/effective-policy
→ {
    current: "needs_approval" | "skip",
    available: ("needs_approval" | "skip")[],  // 用户被允许切换到的选项
    locked_tools: string[],                    // 无论策略如何始终强制审批的工具
  }

// 切换策略
PATCH /v1/sessions/{id}/approval-policy
  { policy: "needs_approval" | "skip" }
```

选择器外观规则：
- `needs_approval`：橙色 `⚠` 图标
- `skip`：绿色 `✓` 图标
- `available` 中没有 `skip` 时，该选项置灰并 tooltip 提示「需要管理员授权」
- `locked_tools` 非空时，选择器底部展示锁定工具提示（不影响其他工具策略切换）

细节规则：
- 自动扩展高度，最多 8 行，超出内部滚动
- `⌘↵`（Mac）或 `Ctrl+Enter`（Windows/Linux）发送；`Enter` 换行
- 拖拽文件到输入框自动触发上传
- 粘贴图片直接作为附件添加
- `@` 触发文件引用选择器（从 Files 中选择已上传文件）
- 模型选择器、运行模式、权限模式均作用于**当前会话**，不影响全局默认配置

#### 会话标题

由后端 AI 异步生成，取会话首轮内容自动总结。前端处理：
- 生成完成前侧边栏显示 `─ ─ 生成中...`（灰色占位）
- 标题生成后通过 SSE 事件 `session.title_updated` 推送，前端实时替换
- 用户可随时点击标题手动修改

## 4. 通知系统

### 4.1 Electron 桌面通知

**系统托盘图标状态**：

```
⬡  (灰色)     → 未连接 Server
⬡  (蓝色)     → 空闲，Server 已连接
⬡⟳ (蓝色转圈) → 有任务运行中
⬡! (橙色感叹) → 有审批等待（最高优先级）
```

**桌面通知触发场景**：

| 场景 | 通知级别 | 示例文案 |
|------|---------|---------|
| 有工具审批等待 | 强制弹出 | `Talos 等待你的确认：exec_command` |
| Agent 任务完成 | 可配置 | `分析项目依赖 已完成` |
| Server 断连 | 强制弹出 | `Talos Server 连接中断` |
| 会话执行出错 | 可配置 | `部署前检查 执行出错` |

### 4.2 Web 端通知

- 使用 Browser Notification API（需用户授权）
- 页面不可见时触发，页面可见则只显示 in-app 提示
- 有审批等待时页面 title 前缀变为 `[1] Talos`

### 4.3 In-app 通知

Approvals 角标和侧边栏 `⏸` 状态是主要提示，无单独通知中心。

## 5. 交互细节

### 5.1 侧边栏行为

- 默认 260px 展开状态
- 窗口宽度 < 1024px 时自动折叠为 56px 图标模式
- 移动端（< 768px）为抽屉式覆盖层
- 历史会话 hover 时右侧出现 `···` 操作菜单（重命名 / 删除）
- `⌘K` 全局搜索历史对话

**会话列表规则**：
- 按 Project 维度展示，扁平排列，**不做时间分组**（无 Today/Yesterday/ACTIVE 等分组）
- 列表顺序：运行中/等待审批的会话置顶，其余按 `updated_at` 倒序
- 顶部 `≡` 图标可按状态筛选（全部 / 运行中 / 等待审批），不是分组
- `⌘K` 命令面板支持跨项目搜索会话标题

### 5.2 快捷键

| 快捷键 | 功能 |
|--------|------|
| `⌘K` | 打开全局搜索/命令面板 |
| `⌘N` | 新建对话 |
| `⌘↵` | 发送消息 |

### 8.1 运行模式与连接策略

| 模式 | 连接目标 | Server 来源 |
|------|---------|-----------|
| **云端** | Settings 中配置的 `serverUrl` | 独立部署的 Talos Server |
| **本地** | `http://localhost:{port}` | 前端（Electron）内嵌启动的 Talos Server 子进程 |

本地模式下，前端（Electron 主进程）负责：
1. 检查本地是否已有 Talos 进程在运行（端口探测）
2. 若无，`child_process.spawn` 启动 `talos-server --embedded`
3. 监听进程就绪信号后再建立 SSE 连接
4. 窗口关闭时发送终止信号给子进程

Web 端（非 Electron）**不支持本地模式**，选择器中「本地」选项置灰并提示「本地模式仅在桌面客户端可用」。

### 8.2 与 Talos Gateway API 对接

#### 实时事件（SSE）

所有客户端启动后建立两个 SSE 连接：

```typescript
// ── 全局事件流（状态同步，所有 session 共用）──────────────────
// 职责：轻量状态通知，不承载 transcript 内容
// seq 约束：全局流不带 seq，事件之间无顺序依赖，前端幂等处理即可
// （session.status_changed 等属于此流，不受 transcript seq 规则约束）
GET /v1/events
→ Content-Type: text/event-stream

// 事件结构: { type: GlobalEventType, data: ... }
// session.status_changed  { id, status: SessionStatus }
// session.title_updated   { id, title: string }
// agent.task_started      { session_id, trigger: "autonomous"|"user" }

// ── 单会话 TranscriptEvent 流（历史与实时共用同一模型）──────────
// seq 约束：所有事件携带 session 级单调序号，用于补流去重
// after_seq=N 语义：返回 seq > N 的事件（开区间，N 本身不重发）
GET /v1/sessions/{id}/stream
GET /v1/sessions/{id}/stream?after_seq=N   ← 重连补流，N 为客户端已处理的最大 seq
→ Content-Type: text/event-stream

// 复用后端 TalosOutputItem 类型体系（见 session-history-canonicalization-and-tui-replay-design.md）
// 每个 SSE 事件结构: { type: TranscriptEventType, data: ... }
//
// ── 增量（streaming 阶段）──
// output_text_delta      { call_id, text_delta }          ← AI token 追加
// reasoning_delta        { call_id, text_delta }          ← thinking token 追加
// tool_call_started      { call_id, tool_name, args }     ← 工具开始
// tool_call_completed    { call_id, result, duration_ms } ← 工具完成
// tool_call_error        { call_id, error }
// approval_requested     { call_id, tool_name, args }     ← 需要审批，Agent 阻塞
// approval_resolved      { call_id, approved: bool }      ← 审批结果（任意客户端操作）
//
// ── 提交（turn 完成后）──
// message_committed      { turn_id, items: TalosOutputItem[] } ← turn 完成，写入历史
// done                   {}                                     ← 本次流结束
// error                  { message }

// ── 历史接口（复用同一 TalosOutputItem 结构）──────────────────
GET /v1/sessions/{id}/turns
→ [{ turn_id, seq, timestamp, items: TalosOutputItem[] }]
// items 数组顺序即回放顺序，不依赖 timestamp 二次排序
// 与 SSE 流共享 TalosOutputItem 语义，前端同一套渲染逻辑处理历史和实时
```

## 9. MVP 范围界定

> **原则**：Web MVP 只覆盖云端模式。Electron 相关的任何交互（本地模式、桌面通知、系统托盘、文件选择器、子进程管理）全部移入 Phase 2，不在 Web MVP 中实现，也不污染 Web MVP 的路由、输入框和 API 合同。

## 10. 设计理念总结

Talos Web UI 的核心设计信念是：**这不是一个聊天工具，而是一个 Agent 的控制台**。

用户与 Talos 的关系不是"对话"，而是"委托与监督"：

1. **委托层**：用户告诉 Agent 要做什么，然后可以离开——Agent 自主完成。
2. **监督层**：关键操作的审批卡片**内联在消息流中**，用户随时可以介入或终止。
3. **回顾层**：任务完成后，用户通过对话历史和审计日志了解 Agent 做了什么。

界面设计的一切都在服务这三个层次：侧边栏的状态图标是监督入口，消息流内联审批是授权，Chat 历史是回顾。

## 12. 已决策的关键契约（Open Questions 结论）

### 12.1 SessionStatus 统一术语

全文统一使用以下枚举值，前端 TypeScript 类型、SSE 事件、侧边栏图标文案均以此为准：

| 值 | 含义 | 侧边栏图标 |
|----|------|----------|
| `running` | Agent 正在执行 | `⟳` 蓝色 |
| `waiting_approval` | 等待工具审批，Agent 阻塞 | `⏸` 橙色 |
| `done` | 已完成 | `⌥` 灰色 |
| `error` | 执行出错 | `✗` 红色 |

SSE `session.status_changed` 事件的 `status` 字段必须使用上述四个值，不允许其他写法（`waiting` / `complete` 等均为错误）。

### 12.2 状态管理分工

| 状态类型 | 方案 | 说明 |
|---------|------|------|
| 服务端状态（项目列表、会话列表、Memory、Files） | **TanStack Query** | 负责缓存、失效、重新获取 |
| 流式 token、当前会话 transcript（高频更新） | **Zustand** | 避免 Query 管理高频追加的 draft 状态 |
| 全局连接状态、审批策略 | **Zustand** | 跨组件共享的轻量状态 |
| 组件本地 UI 状态（弹窗、hover） | **useState** | 就近管理，不上升全局 |

设计文档提到"Zustand"的地方均指上述分工，不代表全量使用 Zustand 替代 Query。

### 12.3 Thinking（思考过程）定位与展示范围

**定性为可选的调试/高级功能，不作为产品核心承诺**，展示规则写死如下：

- 默认折叠，用户主动展开才可见
- **可出现在实时 transcript 中**（`reasoning_delta` 事件驱动，实时追加到折叠块）
- **刷新页面后默认不从历史恢复**：`GET /v1/sessions/{id}/turns` 返回的 canonical `items[]` 不包含 `reasoning` 类型，前端不渲染历史 thinking 块
- 如需保留 thinking 内容，只能走单独 debug artifact 接口，不进入 canonical turn items（与 `spec/session-history-canonicalization-and-tui-replay-design.md` §4.4 一致）
- 模型不支持 thinking 时，服务端不发 `reasoning_delta` 事件，UI 静默不展示折叠块

#### 12.4.2 TranscriptEvent（SSE 单会话流事件）

**所有事件必须携带 `session_id`、`turn_id`、`seq` 三个基础字段**，防止重连/补流/并行工具交织时乱序。`seq` 为 session 内单调递增整数，从 0 开始，每个事件严格 +1。

```typescript
interface TranscriptEventBase {
  session_id: string;
  turn_id:    string;   // 同一 turn 内的事件共享 turn_id
  seq:        number;   // session 级单调序号，重连后用于补流去重
}

// ── 增量事件（streaming 阶段）────────────────────────────────────

interface OutputTextDeltaEvent extends TranscriptEventBase {
  type: 'output_text_delta';
  call_id:    string;   // 同一 assistant message 的多段 delta 共享 call_id
  text_delta: string;
}

interface ReasoningDeltaEvent extends TranscriptEventBase {
  type: 'reasoning_delta';
  call_id:    string;
  text_delta: string;
}

interface ToolCallStartedEvent extends TranscriptEventBase {
  type:      'tool_call_started';
  call_id:   string;
  tool_name: string;
  args:      Record<string, unknown>;
}

interface ToolCallCompletedEvent extends TranscriptEventBase {
  type:        'tool_call_completed';
  call_id:     string;
  result:      string;
  duration_ms: number;
}

interface ToolCallErrorEvent extends TranscriptEventBase {
  type:    'tool_call_error';
  call_id: string;
  error:   string;
}

interface ApprovalRequestedEvent extends TranscriptEventBase {
  type:      'approval_requested';
  call_id:   string;
  tool_name: string;
  args:      Record<string, unknown>;
}

interface ApprovalResolvedEvent extends TranscriptEventBase {
  type:     'approval_resolved';
  call_id:  string;
  approved: boolean;
}

// ── 提交事件（turn 完成）──────────────────────────────────────────

// message_committed：一条 assistant message 已落盘，进入历史真源
// 职责边界：表示"可从历史 API 读到此 turn"，不代表本轮流结束
interface MessageCommittedEvent extends TranscriptEventBase {
  type:  'message_committed';
  items: TalosOutputItem[];  // canonical turn items，不含 reasoning
}

// done：本轮流结束（可能在 message_committed 之后、也可能紧随错误）
// 职责边界：表示"SSE 流已关闭，前端可停止 spinner"，不代表已落盘
interface DoneEvent extends TranscriptEventBase {
  type: 'done';
}

interface ErrorEvent extends TranscriptEventBase {
  type:    'error';
  message: string;
}

type TranscriptEvent =
  | OutputTextDeltaEvent | ReasoningDeltaEvent
  | ToolCallStartedEvent | ToolCallCompletedEvent | ToolCallErrorEvent
  | ApprovalRequestedEvent | ApprovalResolvedEvent
  | MessageCommittedEvent | DoneEvent | ErrorEvent;
```

**message_committed 与 done 职责不得混用**：

| 事件 | 表示 | 前端行为 |
|------|------|---------|
| `message_committed` | turn 已落盘，历史 API 可读 | 将 items 写入历史缓存，使 TanStack Query 失效触发刷新 |
| `done` | 本轮流结束 | 停止 spinner，关闭 streaming 状态 |

---

#### 12.4.3 EffectiveApprovalPolicy

```typescript
// server-evaluated，不由前端自行推断
interface EffectiveApprovalPolicy {
  current:      'needs_approval' | 'skip';
  available:    ('needs_approval' | 'skip')[];  // 当前用户被允许切换到的选项
  locked_tools: string[];                       // 始终强制审批，不受 skip 影响
}

// skip 的边界约束（写死，不得放宽）：
// 1. skip 仅对 locked_tools[] 之外的 tool 生效
// 2. skip 是 session 级运行策略，不修改用户全局治理配置（ToolGovernanceSpec）
// 3. 用户切换 skip 后，服务端仍按 ToolGovernanceSpec 决策 locked_tools，
//    前端无权在本地绕过 locked_tools 的审批卡片展示
```

### 12.5 事件到前端动作的映射表

前端 SSE 客户端收到事件后的标准处理行为，不允许自由发挥：

#### Transcript 流（有 seq，session 级）

| 事件 | seq 约束 | 前端动作 | 状态副作用 |
|------|---------|---------|-----------|
| `output_text_delta` | 有 | 按 `call_id` 追加 token 到 Zustand draft | — |
| `reasoning_delta` | 有 | 按 `call_id` 追加到折叠 thinking 块（**不持久化**） | — |
| `tool_call_started` | 有 | 在 draft 中插入 `running` 工具卡片 | — |
| `tool_call_completed` | 有 | 卡片 → `done`，填入 result 和 duration_ms | — |
| `tool_call_error` | 有 | 卡片 → `error` | session → `error`（若后续无 done）|
| `approval_requested` | 有 | 在消息流中插入审批卡片 | session → `waiting_approval` |
| `approval_resolved` | 有 | 更新审批卡片（approved/rejected） | session → `running` |
| `message_committed` | 有 | 写入历史缓存；使 `sessions/{id}/turns` Query 失效 | — |
| `done` | 有 | 停止 spinner，清除 draft | session → `done` |
| `error` | 有 | 展示错误态消息气泡 | session → `error` |
| **重连** | — | 用最后已知 `seq` 发 `?after_seq=N`（返回 `seq > N`） | — |

#### 全局流（无 seq，跨 session）

| 事件 | 前端动作 | 备注 |
|------|---------|------|
| `session.status_changed` | 更新 Zustand store 中对应 session 的 status；更新侧边栏图标 | 幂等处理，无顺序依赖 |
| `session.title_updated` | 更新侧边栏标题（替换占位符） | 幂等 |
| `agent.task_started` | 如当前未在该 session 页面，可显示 in-app 提示 | 可忽略不报错 |

```typescript
  last_used_at: number;

// ── SessionStatus ──────────────────────────────────────────────
// 四个值为全集，禁止使用别名（waiting / complete 等）
export type SessionStatus = 'running' | 'waiting_approval' | 'done' | 'error';

export interface Session {
  id:         string;
  project_id: string;
  title:      string | null;   // null = 标题生成中
  status:     SessionStatus;
  model:      string;
  created_at: number;
  updated_at: number;
}

// ── EffectiveApprovalPolicy ────────────────────────────────────
// server-evaluated，前端不推断，直接渲染
// skip 仅对 locked_tools 之外的工具生效；不修改全局 ToolGovernanceSpec
export interface EffectiveApprovalPolicy {
  current:      'needs_approval' | 'skip';
  available:    ('needs_approval' | 'skip')[];
  locked_tools: string[];
}

// ── TranscriptEvent ────────────────────────────────────────────
// 所有事件必须携带 session_id / turn_id / seq（单调递增，从 0 开始严格 +1）
export interface TranscriptEventBase {
  session_id: string;
  turn_id:    string;
  seq:        number;
}

export interface OutputTextDeltaEvent extends TranscriptEventBase {
  type: 'output_text_delta';
  call_id:    string;
  text_delta: string;
}
export interface ReasoningDeltaEvent extends TranscriptEventBase {
  type: 'reasoning_delta';
  call_id:    string;
  text_delta: string;
}
export interface ToolCallStartedEvent extends TranscriptEventBase {
  type:      'tool_call_started';
  call_id:   string;
  tool_name: string;
  args:      Record<string, unknown>;
}
export interface ToolCallCompletedEvent extends TranscriptEventBase {
  type:        'tool_call_completed';
  call_id:     string;
  result:      string;
  duration_ms: number;
}
export interface ToolCallErrorEvent extends TranscriptEventBase {
  type:    'tool_call_error';
  call_id: string;
  error:   string;
}
export interface ApprovalRequestedEvent extends TranscriptEventBase {
  type:      'approval_requested';
  call_id:   string;
  tool_name: string;
  args:      Record<string, unknown>;
}
export interface ApprovalResolvedEvent extends TranscriptEventBase {
  type:     'approval_resolved';
  call_id:  string;
  approved: boolean;
}
// message_committed：turn 已落盘，进入历史真源
// 职责边界：触发历史 Query 失效；不代表本轮流结束
export interface MessageCommittedEvent extends TranscriptEventBase {
  type:    'message_committed';
  items:   TalosOutputItem[];   // canonical，不含 reasoning
}
// done：本轮流结束，停止 spinner
// 职责边界：不代表已落盘（done 可能在 message_committed 之前到达）
export interface DoneEvent extends TranscriptEventBase {
  type: 'done';
}
export interface ErrorEvent extends TranscriptEventBase {
  type:    'error';
  message: string;
}

export type TranscriptEvent =
  | OutputTextDeltaEvent | ReasoningDeltaEvent
  | ToolCallStartedEvent | ToolCallCompletedEvent | ToolCallErrorEvent
  | ApprovalRequestedEvent | ApprovalResolvedEvent
  | MessageCommittedEvent | DoneEvent | ErrorEvent;

// ── GlobalEvent（全局流，无 seq）─────────────────────────────
export type GlobalEvent =
  | { type: 'session.status_changed'; id: string; status: SessionStatus }
  | { type: 'session.title_updated';  id: string; title:  string }
  | { type: 'agent.task_started';     session_id: string; trigger: 'autonomous' | 'user' };
```

### 13.3 需扩展接口（⚠️）

路由已存在，但结构或语义存在差异，需后端配合调整后前端再对接：

#### `POST /v1/sessions/{id}/messages`（流式行为）

- **现状**：支持 `{ stream: true }` 参数，返回 inline request-bound SSE 流，连接随响应结束而关闭。
- **差异**：Spec 定义了独立的持久化 Transcript 流（`GET /v1/sessions/{id}/stream`），
  前端 SSE 客户端应使用持久化流，而非绑定在 POST 响应上。
- **建议**：POST messages 继续返回 `{ request_id, ... }` JSON 响应（`stream: false` 或不传），
  流式内容通过独立的 `GET /v1/sessions/{id}/stream` 推送。
  后端可保留 inline stream 作为过渡（已有 TUI 依赖），但前端 MVP 直接使用独立流。

#### `PATCH /v1/sessions/{id}`（结构变更）

- **现状**：只支持 `conf.agent.model`（字符串）和 `project_root` 两个字段。
- **差异**：Spec 需要支持切换审批策略（`approval_policy`），且 `conf` 是松散 HashMap，
  不符合项目强类型约定。
- **建议**：后端扩展 PATCH body 增加 `approval_policy` 字段；长期将 `conf` 重构为强类型结构体。

#### `GET /v1/sessions` + `SessionRecord` 响应结构

- **现状**：`SessionRecord` 包含 `id, title, context, model, created_at, last_activity, message_count, usage, conf`，缺少：
  - `status: SessionStatus`（`running | waiting_approval | done | error`）
  - `project_id`（当前无 Project 概念，project_root 在 context 内）
- **建议**：后端在 `SessionRecord` 中增加 `status` 字段；Project 概念新增后补充 `project_id`。

#### `GET /v1/sessions/{id}/turns` 响应结构

- **现状**：返回 `Vec<TalosMessageResponse>`（含 `request_id, message_id, output, reasoning, stop_reason, usage`）。
- **差异**：Spec 期望 `[{ turn_id, seq, timestamp, items: TalosOutputItem[] }]`，items 中不含 reasoning。
- **建议**：后端新增专用历史 DTO，与 `TalosMessageResponse`（面向调用侧）分离；
  或在现有结构上增加 `turn_id`、`seq`、`timestamp` 字段并过滤 reasoning。

#### SSE 事件格式（TranscriptEvent）

- **现状**：`TalosEvent` 结构为 `{ event_type, message_id, session_id, sequence, payload }`；
  SSE 事件名为 `message.output.delta`、`message.tool_call.pending_approval` 等。
- **差异**：Spec 定义 `TranscriptEventEnvelope { session_id, turn_id, seq, ...payload }`；
  事件 type 值为 `output_text_delta`、`approval_requested` 等（snake_case，无 `message.` 前缀）。
  字段名 `sequence` → `seq`，`message_id` → `turn_id`。
- **建议**：后端实现独立的 `GET /v1/sessions/{id}/stream` 端点时，使用 Spec 定义的新 DTO；
  现有 inline stream 格式可保持不动（已有 TUI 客户端依赖）。

### 13.4 需新增接口（🆕）

按优先级分组，前端 MVP 仅依赖 P0 接口：
