# Talos v0.1.9

Talos 0.1.9 adds shared Computers, distributed execution, and account data
synchronization across management hosts. Talos's own code is now licensed under
Apache License 2.0; third-party components retain their respective licenses.

## Computers and distributed execution

- Manage local and remote Computers through the shared product APIs and UI,
  with account ownership, hardware information, and live availability.
- Desktop automatically enrolls its embedded Worker after cloud sign-in and
  restores its saved Computer identity after restart. Standalone Workers use
  explicitly provisioned node credentials.
- Workers can connect outbound to the registration hub, allowing execution
  behind NAT without an inbound public Worker port. Direct TLS RPC remains
  available for explicitly configured deployments.
- Select the Computer for a workspace and run its sessions, tools, and resource
  operations there. Each Session stays bound to its Computer; callbacks return
  to the management host coordinating the current execution.
- Desktop retains its own management runtime, database, and local Worker,
  including independent local use when cloud services are unavailable.

## Account synchronization

- Synchronize account data between management hosts through the independent
  Talos Sync service, using the public Cloud and Sync SDK packages.
- Continue an idle Session from another authorized management host on the same
  Computer. Synchronization does not move workspace files or transfer an active
  Turn to another Worker.
- Enable or disable sharing per host/account, with persisted choices, recovery,
  and account isolation. Deployment policy can disable synchronization while
  retaining Computer RPC execution.

## Fixes and upgrade behavior

- Restore anonymous embedded TUI operation and load complete conversation
  history before applying incremental events.
- Preserve cancellation settlement and route OAuth/resource callbacks through
  the currently admitted Worker execution.
- Keep Direct Worker listeners available until in-flight registration and
  unregister finish during shutdown.
- Correct Computer admission cleanup, connection availability, sidebar focus,
  and settings navigation.
- Apply Linux denied-file masking and declare the sandbox's own Tokio features.
- Repair legacy pre-0.1.8 history artifacts and remove completed migration
  artifacts through the existing Product Upgrade lifecycle.

## Packaging and release checks

- Include `LICENSE`, `NOTICE`, and `THIRD_PARTY_NOTICES` in product packages and
  Server/Worker images, with package-content verification before asset upload.
- Include the Linux sandbox launcher beside Server, Worker and TUI binaries,
  and verify it after native TUI installation.
- Use public SDK dependencies for product builds. Authentication E2E fixtures
  accept a separately supplied `cloud-server` executable.
- Run the complete source gate automatically on candidate-branch pushes and
  reuse it for tagged builds, with one validated Cargo dependency resolution.
  Preserve Markdown release notes in annotated tags and validate them locally
  before publication.
- Publish releases from the Talos source repository through one required gate
  covering source checks, frontend checks, product builds, native TUI installation,
  and multi-architecture Server/Worker images. Historical downloads remain in
  the release archive repository.

## Upgrade guidance

Upgrade Server, Desktop, Web, SDK clients, and Workers together to preserve
protocol and data compatibility. Before starting a data migration, stop writers
and retain a verified database backup, matching binaries/configuration, and
required workspace/provider artifacts. Rollback restores the matching backup
and binaries; a binary-only downgrade is unsafe. See the
[deployment and rollback guide](../../deploy/README.md#data-upgrades-and-rollback).

The default service roles are Cloud identity/API at `api.talos.love`, Computer
registration/RPC at `agent.talos.love`, and account synchronization at
`sync.talos.love`. These defaults do not establish that the Computer hub has
been deployed or that cross-physical-machine acceptance has passed.
